# VAS2Font Web Application Design

## Document status

- Status: Approved
- Audience: Project maintainer and implementation agents
- Implementation constraint: This document is the baseline for web development
- User interface language: English only
- Internationalization: Out of scope

## 1. Purpose

VAS2Font converts handwriting created in vas into an OpenType font. The existing command-line pipeline already demonstrates the complete technical path:

1. Generate a versioned PDF writing template from a character set and a coordinate manifest.
2. Import the PDF into vas and write characters in the designated cells.
3. Export the vas notebook and extract `notebook.json` from the ZIP archive.
4. Upload the JSON file and select the matching character set template and version.
5. Extract vector strokes, generate glyph outlines, normalize glyph geometry, and build an installable OTF font.
6. Preview and download the generated font in a browser.

The web application should make this workflow accessible without requiring accounts while preserving the simplicity of the existing engine.

## 2. Product principles

- The handwriting-to-font workflow is the primary feature.
- No registration, login, password recovery, organization, or role system is required.
- A high-entropy project access code grants full access to one project.
- Users can divide writing across multiple uploads and replace selected characters through priority ordering.
- Built-in and custom character set templates use the same generation and validation pipeline.
- PostgreSQL is the only durable data store.
- Generated font files and generated PDF files are not stored persistently.
- The application should favor explicit, deterministic behavior over hidden automation.

## 3. Scope

### 3.1 Initial scope

- Create, open, edit, and delete projects.
- Edit font family and font version metadata.
- List built-in templates.
- Create project-scoped custom character set templates.
- Generate and download PDF writing templates.
- Upload and validate vas `notebook.json` files.
- Select the exact template used by each upload.
- Reorder upload priorities and delete uploads.
- Merge glyphs from multiple uploads by priority.
- Generate an OTF font on demand.
- Preview the generated font with user-provided text.
- Download the same generated bytes used for the preview.
- Soft-delete user-owned records.

### 3.2 Non-goals for the initial implementation

- User accounts and authentication providers.
- Public project discovery, search, or a project directory.
- Collaborative presence, comments, or fine-grained permissions.
- Restoring deleted projects or records.
- Physical deletion or a data retention purge.
- Uploading ZIP archives, images, PDFs, or other vas resources.
- Editing individual glyphs in a browser-based vector editor.
- Kerning, ligatures, variable fonts, color fonts, and vertical writing support.
- Grapheme-cluster or multi-code-point glyph creation.
- Byte-for-byte deterministic font binaries across different software versions.
- A distributed task queue for small initial character sets.
- Internationalization.

## 4. Terminology

- **Project**: A font workspace containing metadata, custom templates, and ordered uploads.
- **Project ID**: A non-secret UUID used in URLs and API paths.
- **Access code**: A high-entropy bearer credential that grants full project access.
- **Template**: A named and versioned character set together with its layout manifest.
- **Built-in template**: A globally available template whose `project_id` is null.
- **Custom template**: A template owned by one project.
- **Upload**: One validated vas notebook JSON document associated with a template.
- **Position**: The priority of an upload. Position 1 has the highest priority.
- **Glyph source**: The strokes and template metrics extracted for one Unicode code point from one upload.
- **Pipeline version**: The version of the font generation behavior used by a project.
- **Active record**: A record whose `deleted_at` value is null.

## 5. User workflows

### 5.1 Create a project

1. The user opens the home page and selects **Create project**.
2. The user enters a font family and a font version.
3. The application validates the metadata and creates the project.
4. The application generates a new access code and displays it once.
5. The user copies and stores the access code before entering the project.

The completion page must state:

- The code grants full read, write, and delete access.
- Anyone with the code can modify the project.
- The code cannot be recovered if lost.
- The code must not be shared publicly.

### 5.2 Open an existing project

1. The user selects **Open project** on the home page.
2. The user enters the access code.
3. The server validates the code against active projects.
4. The application opens the project without placing the access code in the URL.

Invalid, deleted, and malformed access codes produce the same generic failure response.

### 5.3 Create and use a custom template

1. The user opens the Templates section of a project.
2. The user enters a template name, version, and a sequence of characters.
3. The server normalizes and validates the sequence.
4. The server creates a custom template and its coordinate manifest.
5. The user downloads the generated PDF.
6. The user imports the PDF into vas and writes the characters.
7. The user exports the notebook, extracts `notebook.json`, and uploads it with the selected template.

The same workflow supports a correction template containing only characters that should be rewritten.

### 5.4 Upload handwriting

1. The user selects **Upload notebook**.
2. The user selects a `.json` file and an exact template name and version.
3. The server validates the file, the vas format, the PDF page references, the cell assignments, and the extracted glyph coverage.
4. The server stores the raw notebook as JSONB only after complete validation succeeds.
5. The new upload receives position 1 and becomes the highest-priority upload.
6. Existing active uploads are shifted down in the same transaction.

Validation failures do not create an active upload or change upload ordering.

### 5.5 Reorder or remove uploads

- The Uploads section displays uploads from highest to lowest priority.
- The user can reorder uploads with drag-and-drop and accessible up/down controls.
- Reordering submits the complete ordered list of active upload IDs.
- The server validates and applies the order in one transaction.
- Deleting an upload soft-deletes it and compacts the remaining active positions.
- Deleted uploads do not participate in font generation.

### 5.6 Generate, preview, and download a font

1. The user selects **Generate font**.
2. The server merges the active glyph sources and generates an OTF font.
3. The browser receives the font bytes and creates an in-memory Blob and object URL.
4. A temporary `@font-face` rule registers the font for preview.
5. The user enters arbitrary preview text in a textarea.
6. A separate preview region renders the text with the generated font.
7. The user downloads the same Blob without triggering another generation.

Unsupported characters may use the configured fallback font. The interface must indicate the number of generated code points and warn that unsupported characters are not included.

Changing project metadata, templates, uploads, or upload ordering invalidates the current client-side preview.

### 5.7 Delete a project

1. The user confirms deletion in the project danger zone.
2. The server soft-deletes the project and its owned uploads and custom templates in one transaction. Uploads are marked inactive before their referenced custom templates are marked deleted, so the active-reference rule remains satisfied.
3. The access code can no longer open the project.
4. Built-in templates are unaffected.

The interface must not describe this operation as permanent erasure of the stored data.

## 6. Project access model

### 6.1 Access code generation

- Generate at least 128 bits of cryptographic randomness using the operating system secure random source through Python `secrets` or an equivalent primitive.
- Present the code in a grouped, copy-friendly form.
- A UUID4 is acceptable, although a grouped Base32 representation is preferred for readability.
- Enforce a unique constraint on the stored access code hash and retry on the extremely unlikely event of a collision.

### 6.2 Storage and transport

- Store only `SHA-256(access_code)` in `projects.access_code_hash`.
- Do not store the raw access code in PostgreSQL.
- Do not place the access code in URLs, query strings, browser local storage, application logs, analytics, or error reports.
- Keep the raw code in the current tab's `sessionStorage` so a refresh can preserve the session without creating a durable cross-session credential store.
- Send the code in `Authorization: Bearer <access-code>` for project-scoped API calls.
- Use same-origin API access and HTTPS in production.

### 6.3 Authorization behavior

- The access code grants read, write, generation, and delete permissions for its project.
- There are no roles or partial permissions.
- Built-in template listing and download are public.
- Custom templates require access to their owning project.
- Every query for a child resource must verify that the parent project is active.
- No endpoint may return a list of all projects.

### 6.4 Abuse controls

- Apply IP-based rate limits to project opening and font generation.
- Apply configurable request size and computation limits.
- Do not reveal whether a submitted access code belonged to a deleted project.

## 7. Character set and template design

### 7.1 Built-in templates

The initial built-in template is:

- `representative-100`, version `1`.

Additional built-ins may include:

- English uppercase and lowercase letters.
- Digits.
- ASCII punctuation.
- GB2312 Han characters.
- Combined GB2312 and ASCII coverage.

Only implemented and validated templates may appear in the built-in catalog. Built-in templates are read-only and cannot be deleted by users.

Built-in definitions must be versioned and loaded through idempotent migrations or an equivalent initialization mechanism. The database manifest, generated PDF, and handwriting extractor must use the same definition.

### 7.2 Custom character normalization

Custom character input is processed as Unicode code points, not arbitrary strings or grapheme clusters.

The normalization process must:

1. Decode the submitted text as UTF-8 through the JSON request parser.
2. Apply NFC normalization.
3. Iterate over Unicode code points.
4. Remove duplicates while preserving the first occurrence order.
5. Exclude whitespace intended to be supplied automatically by the font builder.
6. Reject control characters and unsupported reference-font code points.
7. Enforce configurable character-count limits.
8. Reject an empty result.

The normalized order determines template order unless a separate ordering feature is added later.

### 7.3 Template editing and deletion

- A template name and version identify the current character sequence and layout manifest.
- A template referenced by any active upload must never be edited or soft-deleted in place.
- Changing a custom template with active upload references requires creating a new template version.
- A custom template with no active upload references may be edited in place or soft-deleted.
- Soft-deleting a custom template hides it from new uploads.
- Project-wide deletion marks all owned uploads inactive before marking their referenced custom templates deleted in the same transaction.
- The manifest must include page indexes, cell rectangles, baselines, reference font sizes, and other metrics required for extraction.
- Changing layout behavior requires a new `layout_version`.

### 7.4 PDF generation

- Generate the PDF on demand from the stored manifest.
- Do not store the PDF in PostgreSQL or durable object storage.
- Draw the reference glyph and writing cell from the same layout data.
- Preserve the distinction between square Han cells and proportionally sized Latin, digit, and symbol cells.
- Derive uppercase height, lowercase x-height, ascenders, descenders, baselines, and writing guides from actual reference-font metrics.
- Use uniform X/Y scaling during font conversion; cell width must not become an independent horizontal font-size multiplier.

## 8. Upload parsing and validation

### 8.1 Accepted input

- One `.json` file per upload.
- One exact `template_id` per upload.
- UTF-8 encoded JSON representing a supported vas notebook.
- Only vector notebook data is required; image, PDF, geometry, audio, and video resources are not uploaded.

The application must not rely only on the filename or multipart content type. It must parse and validate the actual content.

### 8.2 Validation stages

1. Enforce request and file-size limits before parsing.
2. Parse JSON with bounded resource usage.
3. Validate the vas format identifier and supported file version.
4. Validate page dimensions, strokes, points, pressure values, pen kinds, and numeric finiteness.
5. Reject unsupported shape or dashed-stroke features until the engine supports them.
6. Resolve pages using `pdfSource.pageIndex`, not notebook array position alone.
7. Resolve the locked PDF image rectangle to map PDF coordinates into vas page coordinates.
8. Ignore empty non-PDF pages.
9. Reject non-empty pages that cannot be associated with the selected template.
10. Assign each stroke to at most one writing cell, using bounded nearest-cell tolerance for minor boundary deviations.
11. Preserve ink outside an assigned cell for diagnostics; do not silently clip it.
12. Produce a validation report containing counts, missing characters, unassigned strokes, and overflow warnings.
13. Store the notebook only if no fatal validation error remains.

Configurable limits must cover file size, page count, strokes per page, points per stroke, template code points, and total stored data per project.

### 8.3 Template mismatch handling

Selecting a template is part of the upload contract because the notebook JSON does not reliably identify the original template. The server must reject page indexes and geometry that are incompatible with the selected template. It must not guess another template after the user has made a selection.

## 9. Multi-upload merge semantics

### 9.1 Ordering

- Position 1 is the highest priority.
- Active positions are unique and contiguous within a project.
- New uploads start at position 1.
- Reordering and deletion are transactional.
- Soft-deleted rows do not occupy active positions.

### 9.2 Merge algorithm

For every active upload, ordered from highest to lowest priority:

1. Extract glyph sources using that upload's referenced template manifest.
2. Consider only code points with successfully extracted, non-empty handwriting.
3. Add a glyph source only if no higher-priority upload has already supplied that code point.

The final font is the union of all supplied non-empty glyphs.

A blank character in a high-priority upload does not erase or override a valid lower-priority glyph. Removing a character from a font is not part of the initial scope and would require a separate explicit feature.

### 9.3 Glyph consistency

Each glyph source retains its own template metrics during extraction. The final font builder applies the current normalization, metrics, compatibility, and serialization rules consistently to the merged set.

## 10. Font generation

### 10.1 Engine

The web application reuses the existing Python-based engine and the pinned Node.js `perfect-freehand` worker:

- Parse vas vector strokes.
- Reproduce vas pressure-sensitive outlines.
- Clean contours with Skia PathOps.
- Apply bounded isotropic normalization against reference glyph metrics.
- Preserve distinct uppercase, lowercase, ascender, descender, symbol, and Han behavior.
- Apply minimum side bearings and prevent horizontal overlap.
- Preserve full-width Han advances where required by the template policy.
- Generate CFF-based OpenType output with FontTools.
- Include `.notdef` and required whitespace glyphs automatically.
- Populate cmap, hmtx, hhea, head, name, post, OS/2, and compatibility metadata consistently.
- Preserve the code-page and style metadata required by Microsoft Word.

TrueType output may remain available in the command-line tool for diagnostics, but the initial web interface exposes OTF only.

### 10.2 Metadata

- The user-editable font family maps to the appropriate OpenType family and full-name records.
- The PostScript name is generated separately from a safe ASCII representation.
- The user-editable version must be validated and mapped consistently to `head.fontRevision` and name ID 5.
- The subfamily is Regular in the initial implementation.
- Additional metadata fields are deferred until there is a concrete need.

### 10.3 Execution model

- Generation is on demand and is not run on the asynchronous event-loop thread.
- CPU-intensive work uses a bounded execution mechanism with configurable concurrency and timeouts.
- The initial implementation may return the OTF in the generation response for small character sets.
- A dedicated background worker and job-status API will be introduced if large character sets exceed interactive latency or memory budgets.
- Redis is not required for the initial implementation.

### 10.4 Persistence and reproducibility

- Do not store generated OTF bytes in PostgreSQL.
- Do not create durable generated-font files.
- A client preview and download share one generated response.
- The same active inputs and the same pipeline version must produce equivalent outlines, metrics, and character coverage.
- Byte-for-byte identity across deployments is not guaranteed in the initial implementation.
- Font timestamps and binary serialization details may vary.
- Behavioral changes to the engine require a new pipeline version.
- Dependency versions and the reference font must be pinned for controlled deployment.

## 11. Browser preview

- Use a unique internal CSS font family for each generated preview rather than injecting the user's font family into CSS.
- Register the font with `@font-face` and a Blob object URL.
- Wait for `document.fonts.load` before declaring the preview ready.
- Use a textarea for input and a separate region with `white-space: pre-wrap` for preview.
- Provide a sensible default preview string covering representative supported characters.
- Show a fallback warning for unsupported code points.
- Revoke obsolete object URLs when replacing or leaving a preview.
- Never send the generated Blob to another service.

## 12. Data model

### 12.1 General conventions

- Use UUID primary keys.
- Use `TIMESTAMPTZ` values stored in UTC.
- Every durable entity has `created_at`, `updated_at`, and `deleted_at`.
- `deleted_at IS NULL` means active.
- There is no `deleted_by` field because the application has no user identities.
- All user-owned deletion is soft deletion.
- Physical deletion is not performed by application workflows.
- All timestamps and audit fields are maintained consistently by the application or reviewed database mechanisms.

### 12.2 `projects`

Required fields:

- `id UUID PRIMARY KEY`
- `access_code_hash` with a unique constraint
- `font_family`
- `font_version`
- `pipeline_version`
- `created_at`
- `updated_at`
- `deleted_at`

Project `updated_at` changes when project metadata or the active inputs to generation change.

### 12.3 `templates`

Required fields:

- `id UUID PRIMARY KEY`
- `project_id UUID NULL REFERENCES projects(id)`
- `name`
- `version`
- `manifest JSONB`
- `layout_version`
- `reference_font_version`
- `created_at`
- `updated_at`
- `deleted_at`

Constraints and rules:

- `project_id IS NULL` identifies a built-in template.
- A custom template must reference an existing project.
- Separate partial unique indexes enforce active name/version uniqueness for built-in and project-scoped templates because PostgreSQL treats null values as distinct in ordinary unique indexes.
- Built-in records are read-only through user APIs.
- Editing or soft-deleting a custom template is forbidden while any active upload references it.
- Soft-deleted upload references do not block custom template editing or deletion.
- Template records are never physically deleted by application workflows.

### 12.4 `uploads`

Required fields:

- `id UUID PRIMARY KEY`
- `project_id UUID NOT NULL REFERENCES projects(id)`
- `template_id UUID NOT NULL REFERENCES templates(id)`
- `position INTEGER NOT NULL`
- `notebook JSONB NOT NULL`
- `original_filename`
- `file_size_bytes BIGINT NOT NULL`
- `sha256`
- `vas_version INTEGER NOT NULL`
- `glyph_count INTEGER NOT NULL`
- `stroke_count INTEGER NOT NULL`
- `validation_report JSONB NOT NULL`
- `created_at`
- `updated_at`
- `deleted_at`

Constraints and rules:

- A partial unique index enforces `(project_id, position)` for active uploads.
- Counts and positions are non-negative or positive as appropriate.
- A custom template must belong to the same project as the upload.
- A built-in template may be used by any project.
- The raw JSON is never written to application logs.

### 12.5 Records intentionally absent

There are no persistent tables for:

- Generated fonts.
- Generated PDFs.
- User accounts.
- Browser sessions.
- Public project catalogs.

A generation job table may be added later if asynchronous large-font generation becomes necessary.

## 13. API contract

### 13.1 General behavior

- API prefix: `/api`.
- JSON request and response bodies use UTF-8.
- Multipart upload is used for notebook files.
- All project-scoped endpoints require the project access code.
- Error responses contain an English machine-readable code, an English message, and optional structured details.
- No error response contains raw access codes or notebook contents.
- Typical status codes are 400, 401, 404, 409, 413, 415, 422, 429, and 500 as appropriate.

### 13.2 Health

```text
GET /api/health
```

Public liveness and readiness behavior may be separated during deployment implementation.

### 13.3 Projects

```text
POST /api/projects
```

Creates a project from font metadata. The response includes the project and the raw access code. This is the only response that contains the raw access code.

```text
POST /api/projects/open
```

Accepts an access code and returns the associated active project. It does not return a list of projects.

```text
GET /api/projects/{project_id}
PATCH /api/projects/{project_id}
DELETE /api/projects/{project_id}
```

Reads metadata, edits font metadata, or soft-deletes the project and its owned records.

### 13.4 Templates

```text
GET /api/templates
```

Returns active built-in templates.

```text
GET /api/projects/{project_id}/templates
```

Returns active built-in templates and active custom templates available to the project.

```text
POST /api/projects/{project_id}/templates
```

Creates a custom template after character normalization and manifest generation. A new version is required when changing a template that has active upload references.

```text
PATCH /api/projects/{project_id}/templates/{template_id}
```

Edits a custom template only when no active upload references it. The normalized character sequence and manifest are updated atomically. An active-reference conflict returns 409 without side effects.

```text
DELETE /api/projects/{project_id}/templates/{template_id}
```

Soft-deletes a custom template only when no active upload references it. An active-reference conflict returns 409 without side effects.

```text
GET /api/templates/{template_id}/pdf
```

Generates and returns a PDF. Built-in templates are public. Custom templates require access to their owning project.

### 13.5 Uploads

```text
GET /api/projects/{project_id}/uploads
```

Returns active uploads from highest to lowest priority without returning notebook JSON in the list response.

```text
POST /api/projects/{project_id}/uploads
```

Accepts one JSON file and one template ID, validates the notebook, stores it, and assigns position 1.

```text
PUT /api/projects/{project_id}/upload-order
```

Accepts the complete ordered list of active upload IDs and applies it atomically.

```text
DELETE /api/projects/{project_id}/uploads/{upload_id}
```

Soft-deletes an upload and compacts active positions.

### 13.6 Font generation

```text
POST /api/projects/{project_id}/font
```

Generates the current merged font and returns OTF bytes as `application/font-sfnt`. A project with no usable glyphs receives a client-readable conflict response rather than an empty font.

## 14. Frontend structure

### 14.1 Home page

- **Create project** card or dialog.
- **Open project** card or dialog.
- No public project list.
- Clear access-code explanation and copy controls.

### 14.2 Project page

Use a small number of focused sections:

- **Overview**: Font metadata and project danger zone.
- **Templates**: Built-in catalog, custom template creation, editing, deletion, and PDF download.
- **Uploads**: Upload form, validation summaries, priority ordering, and deletion.
- **Generate**: Generation action, coverage summary, preview input, preview region, and download action.

### 14.3 Frontend state

- Keep the access code in `sessionStorage`.
- Keep project ID and non-sensitive state in normal application state.
- Invalidate generated preview state after any input change.
- Do not persist generated font bytes across browser sessions.
- Use accessible forms, keyboard-operable priority controls, confirmation dialogs, and visible error messages.
- All interface text is English.

## 15. Security and privacy

- Treat every access code as a full-capability bearer credential.
- Store only access-code hashes.
- Require HTTPS in production.
- Use strict transport, content-type, referrer, and content-security headers appropriate to the deployment.
- Avoid third-party scripts and unnecessary external resource requests.
- Restrict cross-origin access by default.
- Never log authorization headers, raw notebook JSON, preview text, or generated font bytes.
- Validate and sanitize filenames and font metadata.
- Enforce upload, JSON complexity, project storage, rate, concurrency, and generation-time limits.
- Keep database credentials outside source control.
- Explain that soft deletion disables access but retains the underlying records.
- Treat handwriting and preview text as private user content.

## 16. Performance and reliability

- Validate uploads before inserting them.
- Use transactions for project deletion, upload creation, reordering, and deletion.
- Keep notebook JSON out of list responses.
- Add database indexes for active project children, template lookup, and access-code lookup.
- Bound CPU-intensive generation and prevent event-loop blocking.
- Measure memory and latency with both the representative sample and a full GB2312-scale notebook before enabling very large public workloads.
- Introduce asynchronous generation only when measurements justify it.
- Use PostgreSQL backups independently of soft deletion; soft deletion is not a backup strategy.

## 17. Deployment architecture

### 17.1 Application components

- FastAPI serves the JSON API and the built frontend.
- React, TypeScript, and Vite provide the browser application without a large UI component library.
- SQLAlchemy 2 and asyncpg provide PostgreSQL access.
- Alembic provides schema migrations and built-in template initialization.
- The application image contains Python, Node.js, the pinned outline worker dependencies, FontTools, PathOps, ReportLab, and the reference font.
- Docker Compose runs the application and PostgreSQL with a named database volume.
- A production reverse proxy terminates TLS and applies appropriate request limits.

### 17.2 Configuration

Expected configuration includes:

- PostgreSQL connection settings.
- Trusted proxy and host settings.
- Upload and storage limits.
- Rate-limit settings.
- Generation concurrency and timeout settings.
- Static asset and logging configuration.

No account-related secrets or session infrastructure are required.

## 18. Verification strategy

### 18.1 Project access

- Create a project and verify that the raw code appears only once.
- Open a project with the correct code.
- Reject incorrect, malformed, and deleted-project codes with indistinguishable responses.
- Verify that codes do not appear in URLs or logs.
- Verify that project deletion blocks all child-resource access.

### 18.2 Templates and uploads

- Normalize and deduplicate custom characters without changing their first-occurrence order.
- Reject unsupported and control code points.
- Confirm that PDF geometry and stored manifests agree.
- Confirm that editing or soft-deleting a custom template with active upload references returns 409 without side effects.
- Confirm that the same operations succeed after every referencing upload has been soft-deleted.
- Confirm that project-wide deletion satisfies the same active-reference rule within its transaction.
- Reject wrong template versions, malformed notebooks, invalid coordinates, unsupported stroke types, and oversized inputs.
- Confirm that failed uploads have no transactional side effects.

### 18.3 Priority merging

- Verify that a high-priority glyph replaces the same lower-priority code point.
- Verify that blank high-priority cells do not remove lower-priority glyphs.
- Verify batch union, new-upload priority, reorder atomicity, deletion, and position compaction.

### 18.4 Fonts and preview

- Reopen generated fonts with FontTools.
- Check every cmap entry and glyph with HarfBuzz.
- Render with FreeType and a real browser.
- Run applicable FontBakery OpenType checks.
- Confirm that preview and download use the same Blob.
- Verify unsupported-character fallback behavior.
- Install and exercise the OTF in Microsoft Word on Windows before declaring Office compatibility.

### 18.5 Quality gates

- Python lint and formatting checks pass.
- Frontend type checking, lint, formatting, and production build pass.
- The application production image builds successfully.
- The complete create-to-download workflow passes against the real vas sample.
- No generated artifacts, credentials, or dependency directories enter source control.

## 19. Implementation sequence

### Phase 1: Foundation and projects

- Add the web project structure and environment configuration.
- Add PostgreSQL migrations and data access.
- Implement project creation, access-code opening, metadata editing, and soft deletion.
- Add the home page and project overview.

### Phase 2: Templates

- Refactor the current fixed template generation into manifest-driven built-in and custom templates.
- Implement custom character normalization and validation.
- Implement template listing, creation, active-reference-aware editing and deletion, versioning, and PDF download.
- Add the project Templates section.

### Phase 3: Uploads and priority

- Implement transactional JSON upload validation and JSONB storage.
- Implement upload summaries, ordering, and soft deletion.
- Implement priority-based glyph-source merging.
- Add the project Uploads section.

### Phase 4: Generation and preview

- Expose OTF generation through the API.
- Add bounded execution and generation error handling.
- Implement the browser font preview and same-Blob download.
- Add the Generate section and client-side invalidation.

### Phase 5: Hardening and scale evaluation

- Add rate limits, security headers, resource limits, and operational logging.
- Verify the complete workflow in Docker Compose.
- Test Windows Word compatibility.
- Benchmark larger character sets and decide whether a background worker is required.

## 20. Acceptance criteria

The initial web implementation is complete when all of the following are demonstrated:

1. A visitor can create and reopen a project without an account.
2. The raw access code is never stored in the database or placed in the URL.
3. Project metadata can be edited, and project deletion is soft and effective immediately.
4. A user can create a custom character set and download a matching PDF template.
5. A custom template with active upload references cannot be edited or soft-deleted; the same template can be edited or soft-deleted after every referencing upload is inactive.
6. A real vas `notebook.json` file can be validated and uploaded with an exact template selection.
7. Multiple uploads merge by Unicode code point and priority, including correction uploads.
8. Blank high-priority cells do not erase valid lower-priority glyphs.
9. The application generates a valid OTF containing the merged non-empty glyphs and required automatic glyphs.
10. The browser previews arbitrary text with the generated font and downloads the same bytes.
11. No generated font or PDF is stored persistently.
12. All user data remains in PostgreSQL and uses soft deletion.
13. The complete workflow runs in Docker Compose without modifying vas.
14. The resulting font is verified in Microsoft Word on Windows.

## 21. Future considerations

These items are intentionally deferred and must not block the initial implementation:

- Asynchronous generation for very large character sets.
- Additional built-in character sets.
- More extensive OTF metadata editing.
